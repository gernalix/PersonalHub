## Implementation

History queries existing mutation, verified Git and activity journals, plus the existing applied-patch receipt table. SQL filters precede deterministic keyset pages of 50, and groups are hydrated completely. Deduplication requires a matching transaction/group; distinct operations are retained. External-content FTS4 indexes are disposable search indexes excluded from Git exports, not another event store. Literal prefix tokens use implicit AND, compatible with Android SQLite. Heavy work runs off the UI thread with debounce and stale-request rejection.

The same UI serves global and scoped History; scoped mode hides the module selector. Changes and existing temporal records are distinct modes. Records use stored timestamps and registry `{entity_kind, canonical_id}` targets. Intake navigation now opens its exact original record, generically for every substance. No medicine-name special case exists. Existing Undo engines are reused and unsupported operations do not expose an Undo action.

Settings selects pending patches from the last pulled immutable revision. Review exposes ID/ref/author/schema/tables, previews through the existing sandbox engine, and enables apply only after verified preview and explicit confirmation. The preview ref/hash are rechecked at apply. A durable applied receipt, hash/ref/provenance and data mutations commit in the same transaction; a crash cannot replay a patch. Pull does not apply. Applied patches and Git revision navigation use shared History. Advanced controls reuse existing rebuild, semantic comparison, restore ref/date, milestone and proposal APIs.

FTS integrity commands require a writable SQLite connection even for validation. DatabaseVault permits them in a transaction that always rolls back; backup SHA is unchanged. Exact trigger/schema/FK/identity gates remain enforced.
