# PersonalHub operating rules

- Follow the governing MegaVault protocol before project work.
- For code localization, search `.codex/CODE_MAP.tsv` first using the user's feature/concept/alias and open only the matched primary/related paths. Treat the map as routing hints, not source of truth. Use narrow symbol/path search next and repo-wide search only when the indexed targets are missing, stale, or insufficient.
- Keep `.codex/CODE_MAP.tsv` compact and semantic: update only rows whose feature ownership, important symbol, path, or targeted test materially changed; never turn it into an exhaustive class/function inventory.
- PersonalHub work is serialized by default. Once a task enters device QA/release, do not absorb unrelated commits that arrive on `origin/main`; treat concurrent PersonalHub work as a blocker unless the prompt explicitly declares the work compatible. Re-fetch before the final integration gate, not repeatedly during stable QA.
- Before entering implementation, QA, or release for a PersonalHub roadmap task, acquire the local lease with `python3 tools/personalhub_task_lock.py acquire --prompt-id <PROMPT_ID>`. A second acquire must be reported as BLOCKED, not waited on. Release it explicitly with `python3 tools/personalhub_task_lock.py release --prompt-id <PROMPT_ID>` after PASS, BLOCKED, or FAIL. Stale recovery is allowed only through the tool's TTL checks, never by manually deleting a live lock.
- For emulator-capable Android QA, use `python3 tools/android_emulator_control.py status|start|wait|stop`; use `smoke --timeout 90` only for emulator-infrastructure validation. See `docs/ANDROID_EMULATOR.md`. A successful `start`/`wait` returns the canonical live `target.serial`. The facade resolves the canonical `Pixel_8a` through the existing preflight, prevents unrelated/offline AVD rows from becoming the canonical target, and cleans only processes created by a failed start. Do not duplicate emulator/ADB discovery unless the facade reports a blocker. The older `android_target_preflight.py` CLI remains compatibility-only; treat older project/roadmap text that invokes it directly as stale unless the task explicitly tests the low-level preflight itself.
- `version.txt` is the sole source of truth for both Android `versionCode` and `versionName`. Every future PersonalHub development prompt increments its integer exactly once by `+1`; never derive it from time, Git, or generated source.
- The Home title is always `PersonalHub`; render only the version number, small and discreet, at the bottom-right.
- The default final delivery artifact is the canonically signed debug APK named exactly `<version>.apk` (for example `3.apk`) unless the task explicitly requires a release artifact. Do not minify, ABI-split, post-process or re-sign an APK solely to satisfy a transport-size limit; fix/use the delivery transport instead.
- After the final artifact passes its required gates, treat it as immutable: install that exact file on the Pixel. If it is at or below 50 MiB, send that exact file through the configured Telegram cloud Bot API path. If it is larger, publish it as the current asset of the stable `personalhub-dev-apk` GitHub prerelease and send the release link through Telegram. PersonalHub is private, so that link requires GitHub authentication unless repository visibility changes. A transport failure must not trigger an alternate rebuild that changes the tested artifact.
- Keep the single `personalhub.db`, atomic validated import/export, and crash rollback. Never reintroduce `MigrationActivity`, `:core:migration`, legacy feature databases, or migration-map code.
- Pre-import backups may be removed only when no valid import-pending marker references them. Successful verified imports and startup recovery must clean obsolete pre-import backups.
- Before the first final APK/build/delivery for a change that adds or alters UI, perform one focused source/UI gate for newly exposed values: raw epoch milliseconds, database IDs/UUIDs, cursors, and backend-only encodings must never be user-visible unless the feature explicitly requires them.
- For terminal Git writes in any repository required by a PersonalHub task, resolve the repository's current canonical/default branch from remote state and push that branch; never assume or hardcode `main` versus `master`.
