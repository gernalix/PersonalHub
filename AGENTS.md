# PersonalHub operating rules

- Follow the current MegaVault PersonalHub bootstrap (`ai/personalhubdoc.md`), this repo's `AGENTS.md`/`docs/ANDROID_EMULATOR.md`, and the independent `repo-task`/repo-integrator Git workflow. C2/C3 are retired archives: never invoke their Inbox, allocator, dispatcher, worker or lifecycle helpers, even when old instructions refer to them; do not duplicate orchestration inside PersonalHub. For a Codex goal, use one collision-checked, previously unused six-digit `PROMPT_ID`; carry the same ID across related repos, issue/task branch and handoff, and keep model/reasoning as execution metadata rather than prompt body.
- For code localization, search `.codex/CODE_MAP.tsv` first using the user's feature/concept/alias and open only the matched primary/related paths. Treat the map as routing hints, not source of truth. Use narrow symbol/path search next and repo-wide search only when the indexed targets are missing, stale, or insufficient.
- Before the first Gradle invocation after changing a public Kotlin type/method, DAO API, constructor shape, or Room entity/schema-facing API, run `python3 tools/android_consumer_preflight.py scan --symbol '<exact literal>' ...` for every changed API/symbol that can have consumers. The helper deliberately emits only paths/modules and fails boundedly when a symbol is too broad; do not replace it with repo-wide `rg -n` content dumps. Read only the returned consumer files/blocks and update every affected call site first. For removed/renamed literals, require `python3 tools/android_consumer_preflight.py gate --forbid '<old literal>' ...` to PASS before Gradle. When a constructor/method remains valid but its shape changed, rescan that exact constructor/method and inspect every returned consumer instead of using the obsolete-symbol gate. Only after consumer closure run one quiet compile gate for the highest affected consumer module (`./gradlew :<module>:compileDebugKotlin --quiet --console=plain` when available), then proceed to targeted tests; a compile failure must drive only a leaf correction from the compiler evidence, never a new broad discovery sweep.
- Keep `.codex/CODE_MAP.tsv` compact and semantic: update only rows whose feature ownership, important symbol, path, or targeted test materially changed; never turn it into an exhaustive class/function inventory.
- Treat every `:feature:*` module as an implementation capsule. The `:app` composition root may import feature code only through explicit direct `.api` or `.hub` packages; nested implementation packages remain private. Features must not depend on or directly import another feature implementation; contracts must remain implementation-free; core must never depend on a feature. Each feature owns its Android Activities/receivers/providers/services and public shortcut alias in its own manifest; the host manifest must never declare a feature implementation component or embed private feature Activity class names. Run `./gradlew checkArchitectureBoundaries` after any change to module wiring, public integration entrypoints, persistence ownership, manifests, or feature package boundaries.
- When Android device/UI QA or performance profiling is needed, use the installed `$test-android-apps` plugin where applicable: its `android-emulator-qa` and `android-performance` skills provide UI/logcat/screenshots and Perfetto/Simpleperf/gfxinfo evidence. It is optional when no such evidence is needed. The plugin does **not** own emulator startup, APK distribution, safety, or device selection; the current MegaVault/PersonalHub protocol takes precedence over generic plugin adb/Gradle recipes.
- For emulator-capable Android QA, strictly follow the current MegaVault PersonalHub device protocol and `docs/ANDROID_EMULATOR.md`: use `python3 tools/android_emulator_control.py status|start|wait|stop`; use `smoke --timeout 90` only for emulator-infrastructure validation. A successful `start`/`wait` returns the canonical live `target.serial`. The facade resolves the canonical `Pixel_8a` through the existing preflight, prevents unrelated/offline AVD rows from becoming the canonical target, cleans only processes created by a failed start and keeps a final-stop budget. Do not duplicate emulator/ADB discovery unless the facade reports a blocker. The older `android_target_preflight.py` CLI remains compatibility-only; treat older project/roadmap text that invokes it directly as stale unless the task explicitly tests the low-level preflight itself.
- For PersonalHub public-shortcut runtime QA, use `python3 tools/android_shortcut_alias_smoke.py --serial <canonical-emulator-serial> --apk <exact-built-apk>`. The helper installs that exact artifact with runtime permissions pre-granted, discovers the six feature-owned aliases from source manifests, force-stops between launches, and verifies each alias reaches its declared target. Do not hand-roll shell loops, infer the package from other installed builds, or retry aliases individually unless this helper reports a concrete failure.
- For any Gradle connected Android test acceptance gate, invoke the command through python3 tools/android_connected_test_gate.py -- .... The wrapper preserves nonzero child status and also fails closed on known instrumentation/cleanup false-success markers such as INSTRUMENTATION_FAILED and DELETE_FAILED_INTERNAL_ERROR; never accept BUILD SUCCESSFUL alone as device-test evidence.
- For long Gradle/device commands that may outlive one terminal collection window, launch the command exactly once with a stable process/log handle and poll that same execution. A collection timeout is not evidence to start an equivalent second command; duplicate builds/runs are forbidden unless the first process is confirmed terminated or state materially changed.
- Physical-device androidTests must keep their physical-device safety guards. Never weaken a Pixel/non-generic/non-SDK guard just to make the same test run on the canonical emulator. When acceptance requires emulator QA for behavior previously covered only by a physical-device test, add or use a narrowly scoped emulator-safe test instead; keep physical-only tests physical-only.
- When testing or installing on the physical Pixel would require the user to stop using it, first send and verify **both Fedora desktop and Telegram** notifications through the already configured notification channels, explicitly asking the user to stop using the Pixel. Do not begin that exclusive/disruptive interaction if either notification fails; avoid touching the phone until access is safe. After **all** such interaction has ended, send and verify both completion notifications saying the Pixel can be used again, including after a test failure or cancellation; if the device state remains uncertain, notify that explicitly rather than falsely saying it is free. No pre/post notifications are needed for emulator/TCL or genuinely non-disruptive Pixel checks. This narrow safety exception does not authorize ordinary Telegram progress/status messages or expose credentials.
- For a physical-Pixel APK install, use `python3 tools/android_pixel_apk.py install` after the required build. It resolves the exact debug artifact from Gradle `output-metadata.json`, resolves the physical Pixel through the existing preflight library, and always scopes `adb install -r` to that serial. Do not guess `app-debug.apk`, parse `adb devices` manually, or attempt an unscoped install first.
- For Pixel Perfetto queries, use `python3 tools/android_perfetto_query.py TRACE --query-file QUERY.sql` (or `--query` for short SQL) when the trace path is already known. When the task only needs to reuse the newest existing PersonalHub trace, use `python3 tools/android_perfetto_query.py --latest-trace --query '…'`; the helper searches the known runtime roots and already defaults to the canonical benchmark `trace_processor_shell_aarch64`. Do not probe the processor with `--help`, `rg --files`, `find`, `which`, or manual ADB first; fall back to manual discovery only if the helper reports a concrete blocker.
- For Android UI inspection during QA, use `python3 tools/android_ui_summary.py --serial <serial>` instead of printing raw `uiautomator` XML. When checking a known label/value/error, prefer `--match '<regex>'` so only relevant semantic nodes are emitted. Print the full XML only if the compact helper fails or cannot provide evidence required by the task; do not emit repeated full-tree dumps for routine navigation.
- For emulator-infrastructure unit verification, run only `PYTHONDONTWRITEBYTECODE=1 python3 tools/test_android_emulator_stack.py`. It already runs the historical preflight, regression and facade suites and rejects tracked Python cache artifacts. After PASS, do not rerun those component suites individually. If real host validation is required, add exactly one facade `smoke --timeout 90`; its structured result replaces manual ADB/process checks. For emulator-related tasks, route directly to `tools/android_emulator_control.py`, `tools/android_target_preflight.py`, `tools/test_android_emulator_stack.py` and `docs/ANDROID_EMULATOR.md` instead of doing repo-wide discovery.
- `version.txt` is the sole source of truth for both Android `versionCode` and `versionName`. Each completed and integrated application goal/batch that produces a **new final distributable APK** gets exactly one NV increment, performed centrally by its final-delivery owner from the latest integrated canonical branch immediately before the final build. Ordinary parallel development workers MUST NOT bump it. Commits, docs-only work, tests, QA/benchmark builds and goals without a newly delivered APK do not advance NV. Multiple changes packaged into one distributable get one increment; retries, rebuilds and corrective patches of that same delivery never add increments. Never derive NV from time, Git or generated source.
- Before installing a final APK on the Pixel or publishing/sending it via Telegram/GitHub, automatically verify its **actual packaged manifest** with `tools/verify_apk_version.py`: application ID must be `com.gernalix.personalhub`, and `versionCode` and `versionName` must both match `version.txt` (as must any declared delivery version). This fail-closed gate runs in `tools/android_pixel_apk.py install` and `tools/deliver_personalhub_apk.py`; missing inspection tools or mismatches BLOCK final distribution.
- The Home title is always `PersonalHub`; render only the version number, small and discreet, at the bottom-right.
- The default final delivery artifact is the canonically signed debug APK named exactly `<version>.apk` (for example `3.apk`) unless the task explicitly requires a release artifact. Every final distributable PersonalHub APK MUST be minified before final QA. The canonical sequence is **build → minify → sign → test → install → publish**, and every final device test, Pixel install and delivery must use that exact same byte-identical minified+signed APK. QA/benchmark/test-only APKs are not final delivery artifacts and do not inherit this delivery requirement.
- Minification is a pre-QA build step, never a post-test transport workaround. Once final QA starts, do not rebuild, minify, shrink, zipalign, post-process, re-sign or otherwise mutate the APK. If the minifier changes the artifact, restart final QA on that minified artifact. If the canonical minification step cannot run or produces an invalid artifact, final delivery is BLOCKED rather than silently shipping an unminified APK.
- After the final minified+signed artifact passes its required gates, treat it as immutable: install that exact file on the Pixel. If it is at or below 50 MiB, send that exact file through the configured Telegram cloud Bot API path. If it is larger, publish that exact file as the current asset of the stable `personalhub-dev-apk` GitHub prerelease and send the release link through Telegram. PersonalHub is private, so that link requires GitHub authentication unless repository visibility changes. A transport failure must not trigger an alternate rebuild that changes the tested artifact.
- Keep the single `personalhub.db`, atomic validated import/export, and crash rollback. Never reintroduce `MigrationActivity`, `:core:migration`, legacy feature databases, or migration-map code.
- Pre-import backups may be removed only when no valid import-pending marker references them. Successful verified imports and startup recovery must clean obsolete pre-import backups.
- Before the first final APK/build/delivery for a change that adds or alters UI, perform one focused source/UI gate for newly exposed values: raw epoch milliseconds, database IDs/UUIDs, cursors, and backend-only encodings must never be user-visible unless the feature explicitly requires them.

- An APK build/install is not a database migration. PersonalHub intentionally carries no historical Room migrations in the APK: before installing a schema-incompatible build on a data-bearing device, migrate the live database externally with the checked-in migration runner, preserve a rollback copy, and require its schema/integrity report to PASS. Never use uninstall, clear-data, destructive fallback, or a user_version-only edit as a substitute. All ordinary interactive database-backed Activities must enter through `DatabaseStartupGate` before feature initialization so a stale schema is blocked instead of crashing; dedicated database recovery/import Activities are the explicit exception so a compatible externally migrated database can still be restored.
